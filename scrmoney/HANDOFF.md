# Handoff: Scrmoney — планировщик бюджета

_Обновлено 02.11.2026 (Самара, UTC+4), сессия Codex: читаемые переносы в боковых карточках Плана, v35. Папка: `C:\Users\scrou\Documents\scrmoods\scrmoods-web\scrmoney\` (внутри git-репозитория `scrmoods-web`)._

## Цель
Scrmoney — офлайн-веб-приложение (PWA, один `index.html`) для учёта денег в Грузии: приходы в $/€ с курсом НБГ для налогов, личные расходы, итоги года и главное — **«План»**: простой и «крутой» планировщик бюджета. Пользователь (пишет по-русски, весь интерфейс по-русски) хочет: анкету в стиле Quick Check-in из scrmoods, таблицы как в Excel-шаблоне бюджета на компьютере, цели с накоплением, прогноз на год, выбор основной валюты, стили Classic / Paper («Бумага») / Green apple («Зелёное яблоко») как в scrmoods. Пользователь любит, когда ему задают вопросы перед крупными решениями (AskUserQuestion с вариантом «(Рекомендую)»).

## Решения и почему
- **v27: лимиты = план трат, остаток = копилка** (ответы пользователя: траты «почти никогда» не записывает; остаток — в копилку; при нехватке — предупредить и предложить; проверка раз в месяц по остаткам — да). Факт из «Расходов» не используется для расчёта, только как подсказка «записано». Если лимитов нет — старый расчёт («все свободные деньги») и плашка «Задайте лимиты».
- **v26: правки ячеек cash flow — `budget.cf = {'YYYY-MM': {id: {a, c}}}`** (сумма в своей валюте, чтобы не «плыла» с курсом), применяются в `budgetEvents` (`ov`/`extraM`) — значит влияют на «в день», календарь, копилку, прогноз. **Лимиты по месяцам — `budget.limM = {'YYYY-MM': {кат: лари}}`**, `limFor/limSumFor` (используются в `saveSim`, cash flow, старых таблицах, `dailyCard`). Пользователь выбрал: в окошке спрашивать «только этот месяц / с этого и дальше / вернуть»; «с этого и дальше» меняет правило (`x.a`/`budget.lim`) и записывает старую сумму в месяцы до него. Факт текущего месяца не правится — щелчок ведёт в «Расходы». По умолчанию 12 месяцев вперёд с текущего; прошлое — во вкладке «Год». «+ категория» создаёт категорию расходов (`spCatsUser`). «Повседневное» сворачивается (`planLayout.col['cf:daily']`).
- **v26: история остатков** — `balSnap()` в `saveBudget`: при изменении счетов пишет `budget.accAt` (дата) и `budget.bal[дата] = лари` (≤ 400 записей). Нужна для «обновляли N дней назад» и будущих остатков прошлых месяцев во «Годе».
- **v26: `planView`** — на компьютере `book` | `table` (cash flow), на телефоне `cards` | `table` (старые таблицы); значение одно (`scrmoney.planView`), трактуется по ширине. При переходе через 900 px — перерисовка (`resize`).
- **Один файл `index.html`, без сборки на диске.** У предыдущего агента была сборка из кусков в своём контейнере (`parts/*.js|css` + `build.py`), но контейнер временный — **этих файлов больше нет**. Править нужно прямо `index.html`. Не менять, если пользователь не попросит завести сборку.
- **Всё считается в лари (GEL), показывается в валюте плана.** `baseCur()/bK()/bS()/bm()/gel()` — `gel(x)` выводит сумму в валюте плана, ввод в таблицах умножается на `bK()`. Хранимые значения (`lim`, `fact.*`, `goal.log[].g`) — в лари. Статьи хранят свою валюту (`a`, `c`). **Почему:** смена валюты ничего не ломает. Не менять без миграции данных.
- **Дневной бюджет «сглаженный» на 18 месяцев** (`budgetCalc`: по отрезкам между поступлениями, `rate = min_j (накопленные деньги до j) / дни`), показываем 12. Крупные траты копятся заранее, а не «в последний момент»; 18 — чтобы в 12-м месяце не было всплеска «трать всё».
- **Цели — первыми, в день первой регулярной зарплаты** (`payday`). Если план составлен уже после зарплаты этого месяца — первый взнос со следующей (`skip` в `goalInfo`). Пользователь выбрал «Сначала цели».
- **Средний доход = итог столбца «Факт» таблицы «Доходы» за прошлые месяцы** (`incFactOf`, `avgIncome`, кэш `_avgC` сбрасывается в `saveBudget`/`render`). Текущий месяц не входит. Статья «Средний доход по факту» — `inc` с `kind:'avg'`, у всех доходов выключатель `off`. Пользователь выбрал «только галочки у статей» и «вписывать только в столбце Факт».
- **Записи из вкладки «Приходы» сами попадают в «Факт»** (раскладываются по статьям) и значит в среднее. Это оставлено, но спрошено у пользователя — см. «Открытые вопросы».
- **Лимиты повседневных трат одинаковые на все месяцы** (`budget.lim`, в лари). Предлагалось сделать по месяцам — пользователь не ответил.
- **Выбор месяца цели — два `<select>`**, потому что `input type="month"` не работает в Firefox/Safari на компьютере (пользователь не мог выбрать месяц).
- **Накопления: цели закрываются по очереди** (в порядке списка `budget.goals`), сценарий «весь остаток после обязательных, разовых и повседневных (лимиты, иначе средние из «Расходов», без категории «Дом») — в копилку», старт = накоплено на целях + деньги на счетах сверх запаса.
- **Таблица ежемесячных называется «Обязательные платежи»**, а «Счета» — это где лежат деньги (карта, наличные, вклад), чтобы не путать.
- **Общий бюджет — свой Cloudflare Worker + KV, сквозное шифрование.** Синхронизируются `budget`, `minc`, `spend`, `spCatsUser`, `rows` (с владельцем `by`), `members` (`{id:{n}}`). Пользователь сначала выбрал «План + Расходы», потом попросил и приходы — с владельцем, налог у каждого свой, в плане сумма всех. `recv`/`syncRecv`/`syncBase` из v23 удалены.
- **Формат 2 (v24) — поля с временем правки, не трёхстороннее слияние.** `flatten()` раскладывает документ на поля: элемент списка с id целиком (`["spend","@id"]`), поле объекта, порядок списка (`[..,"#"]`); вложенные списки с id (`budget.goals[].log`) — отдельно; какие списки «с id» — `KEYED`. Время ставит **только `syncRecord` из `store.set`** — сравнение с тем, что вкладка видела (`syncLast`). Поле, значение которого не совпадает с записанным хэшем (`syncClk[path]=[t,hash]`), получает t=0 → проигрывает (так обезврежены отставшие вкладки и старый код). Удаление — только надгробие `syncTomb[path]=t` (180 дней); «нет в списке» ≠ удаление. Слияние `syncMerge`: max(t), при равенстве значение > надгробие, затем по тексту (детерминированно). Пользователь прямо просил «чтобы синхронизировалось самое новое» и «чтобы такого не происходило».
- **Ключ формата 2 — другая соль PBKDF2** (`scrmoney-sync-v2`), шифр с префиксом `2.`. Цель: старые клиенты v23 падают на расшифровке **до** PUT и не могут перезаписать данные. Документ формата 1 читается старым ключом и вливается с t=0.
- **Вкладки:** `storage`-событие перезагружает память и `syncLast` (без записи времени), `navigator.locks` — одна синхронизация за раз; локальное состояние для слияния читается из localStorage (`storeDoc`/`getK`), а от чтения до записи итога нет `await`.
- **SW: страница network-first** (5 с тайм-аут, потом кэш) — чтобы после публикации не запускалась старая версия рядом с новой. Остальные файлы — как раньше.
- **Резервные копии:** `backups` в localStorage (12 шт.): ежедневная, перед удалением с другого устройства, перед подключением/созданием/восстановлением. Worker v2 кладёт прежнюю версию в `h:<room>:<YYYYMMDDHHM>` (раз в 10 мин, TTL 30 дней), `GET /r/<room>/h`. Восстановление = обычная правка (`restoreDoc` → `store.set`), уходит всем; участников не откатывает.
- **id приходов — строки** (`'r'+rowSalt+старый номер` для старых, `newId()` для новых); `rowsFix` применяется при каждом чтении `rows` из хранилища.
- **Чужие правки не применяются**, пока открыта анкета/окно или фокус в поле ввода (`syncCanApply`); синхронизация ждёт (`syncWait`) до `focusout`/закрытия окна. Правки при этом не теряются — у них есть время.
- Durable Objects не взяли: настройка в панели Cloudflare сложнее для пользователя; KV + поля с временем достаточно (порядок записей KV не важен для корректности).
- **Валюта показа и раскладка окошков — на устройстве, порядок строк — в общем плане.** Пользователь выбрал «валюту плана, на всех вкладках» и «строки и сами окошки». Валюта и окошки — личные предпочтения, их незачем навязывать партнёру; порядок доходов/целей — часть плана (порядок целей = очередь накоплений).
- **Старый табличный «План» (v1, ключ `scrmoney.plan`) не показывается**, данные не удалены. План v1 в `scrmoney.budget` мигрирует (`budgetMigrate`, `budgetAccts`).

## Пробовали и отказались
- `input type="month"` для срока цели — не работает в Firefox/Safari на компьютере.
- Жёсткие две колонки таблиц (`.tcol`) — оставляли дыру под короткой колонкой; заменено на CSS `columns: 2 460px` с `break-inside: avoid`.
- Линейный график накоплений — пользователь хотел столбики по месяцам с разделителями и подсветкой.
- Средний доход из «Приходов» + отдельная сумма за месяц как источник — переделано на итог «Факта» по ответу пользователя (сумма «Вписать за месяц», ключ `scrmoney.minc`, осталась и раскладывается в факт).
- **Запись на компьютер через `device_commit_files` по тому же staged-пути** однажды записала старую версию файла. Каждую новую версию класть в новую папку (`/mnt/user-data/outputs/scrmoney-vNN/`) и после записи сверять `sha256sum` на устройстве.

## Известные проблемы и риски
- **Двойной счёт аренды:** если аренда есть и в «Обязательных платежах», и записывается в «Расходы» (категория «Дом»), факт расходов её учтёт дважды. Прогноз «По среднему» по умолчанию не добавляет обязательные, если в «Расходах» есть «Дом» (`fBills`).
- Курс НБГ запрашивается не чаще раза в сутки на адрес (бережём сайт); без курса суммы в валюте считаются как 0 и показывается предупреждение.
- Шрифты стилей (Oswald, IBM Plex Mono, Caveat, Pangolin, Nunito) грузятся с Google Fonts — офлайн будут системные замены.
- Репозиторий публичный (GitHub Pages) — этот `HANDOFF.md` тоже будет опубликован по адресу …/scrmoney/HANDOFF.md. Секретов в нём нет.
- `scrmoods-web/../play-upload-key-PRIVATE` — приватный ключ Android-публикации scrmoods, **не трогать и не читать**.
